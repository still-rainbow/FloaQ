# FloaQ 통신 구조 — 처음 보는 사람을 위한 정리

> 기준: 브랜치 `dev-iot`, 커밋 `7aac94a` (2026-09-23, 9절 "고친 것" 은 그 뒤 커밋) · 코드를 읽어서 정리했다(실행 검증 아님)
> 이 문서 하나로 "무엇이 무엇과, 왜, 어떻게, 얼마나 자주" 이야기하는지 알 수 있게 썼다.
> 발표 자료에 그대로 옮길 수 있도록 **절 하나 = 슬라이드 한 장** 정도로 나눴다.

## 1. FloaQ 는 무엇을 하나

작은 배에서 사람이 물에 빠지면(MOB, Man Overboard):

1. **카메라(Jetson)** 가 물에 빠진 사람을 찾는다
2. **발사관(Pi)** 이 그쪽으로 돌아서 **구명 부표** 를 쏜다
3. 물에 뜬 **부표(아두이노)** 가 자기 위치를 1초마다 무선(LoRa)으로 알려준다
4. 배 안의 **키오스크 화면** 에 사고 상황과 부표 위치가 뜬다
5. 30초 안에 취소하지 않으면 **자동으로 조난 신고** 가 나간다
6. 모든 기록은 인터넷이 될 때 **서버(EC2)** 로 올라가고, 육지의 **관제 웹** 에서 본다

이 과정에서 장치들이 서로 주고받는 모든 연결을 **통신** 이라고 부르고, 이 문서는 그것을 정리한다.

## 2. 등장하는 장치 다섯

| 장치 | 어디에 | 하는 일 | 한 줄 비유 |
|---|---|---|---|
| **Raspberry Pi** | 배 | 모든 통신이 모이는 중심. 사고를 판단하고, 발사관 서보를 돌리고, 기록하고, 서버로 올린다 | 교환대 · 두뇌 |
| **Jetson** | 배 | 카메라 두 대로 사람을 찾고, 거리와 방향을 계산한다 | 눈 |
| **부표 (아두이노)** | 바다 | 물에 뜬 뒤 GPS 위치를 1초마다 무선으로 보낸다 | 물에 뜬 발신기 |
| **키오스크** | 배 (태블릿 화면) | 선원이 사고 상황을 보고 취소·신고·구조 버튼을 누른다 | 조종석 계기판 |
| **EC2 서버 + 관제 웹** | 육지 (인터넷) | 기록을 모아 두고 육지에서 볼 수 있게 한다 | 본부 |

**Pi 가 가운데다.** 다른 장치끼리는 직접 이야기하지 않고 거의 모두 Pi 를 거친다.
(예외 하나: 키오스크는 카메라 영상만 Jetson 에서 직접 받는다.)

## 3. 먼저 알아둘 용어

| 용어 | 쉬운 설명 |
|---|---|
| **MQTT** | 장치끼리 짧은 메시지를 주고받는 방식. **게시판** 과 같다. 보내는 쪽은 게시판에 글을 올리고(publish), 받는 쪽은 관심 있는 게시판을 구독(subscribe)해 둔다 |
| **브로커** | 그 게시판을 운영하는 프로그램. FloaQ 는 Pi 안의 **mosquitto** 를 쓴다 |
| **토픽** | 게시판 이름. 예: `ship/<배ID>/jetson/detection` = "이 배의 Jetson 이 올리는 탐지 게시판" |
| **QoS** | 배달 보장 수준. **0** = 한 번 던지고 끝(빨리, 가끔 잃어도 됨) · **1** = 받았다는 답이 올 때까지 다시 보냄(꼭 가야 함) |
| **retained (고정 글)** | 게시판 맨 위에 고정된 마지막 글. 나중에 들어온 사람도 **들어오자마자** 현재 상태를 본다 |
| **LWT (유언)** | 장치가 갑자기 죽으면 브로커가 대신 올려주는 "나 죽었음" 글 |
| **봉투 (envelope)** | 모든 MQTT 메시지를 같은 모양으로 싸는 겉봉. `{request_id, v, ts, data:[...]}` — 누가 언제 보냈는지, 규격 버전은 몇인지 |
| **HTTP** | 웹 브라우저가 쓰는 요청·응답 방식. 사진처럼 **큰 데이터** 를 올리거나 **한 번 물어보고 답 받기** 에 쓴다 |
| **LoRa** | 전기를 조금 쓰고 **멀리** 가는 대신 **아주 짧은** 데이터만 보내는 무선. 부표처럼 배터리로 오래 버텨야 하는 장치에 맞다 |
| **E22** | LoRa 무선 모듈 부품 이름(Ebyte E22-900T22D). 부표와 Pi 에 하나씩 달려 있다 |
| **UART (시리얼)** | 보드와 부품을 선 두 가닥으로 잇는 가장 단순한 통신. Pi ↔ E22, 아두이노 ↔ E22 가 이것으로 붙는다 |
| **동기화 (sync)** | 배에 쌓아 둔 기록을 인터넷이 될 때 서버로 올리는 것 |
| **ship_id / ship_key** | 배의 이름표 / 배의 비밀번호. ship_key 는 서버에 "진짜 그 배"임을 증명하므로 **절대 밖으로 새면 안 된다** |

|---|---|---|---|---|
| ① | Jetson → Pi | MQTT | "사람 발견", "여기로 조준", "카메라 상태" | 조준 최대 초당 5번, 상태 5초마다 |

| ② | 부표 → Pi | LoRa 무선 | 부표 위치 + 버튼 눌림 (19바이트) | 1초마다 |
| ③ | Pi → 키오스크 | MQTT | 사고 상태, 장치 상태, 부표 위치, 신고 상태 | 부표 1초, 장치 5초 |
| ③ | 키오스크 → Pi | MQTT | 버튼 명령: 취소 · 지금 신고 · 수동 신고 · 구조 · 종료 | 누를 때 |
| ③ | 키오스크 → Pi | HTTP | 배 등록, 지난 사고 기록, 사진, 해양 정보 | 화면 열 때 |
| ④ | Pi → EC2 | HTTPS | 모든 기록(9종) + 사진 묶음 | 10초마다 (밀리면 0.5초) |

## 5. 사고 하나가 처리되는 순서

```
[0초]   Jetson: 좌우 카메라 둘 다 사람을 봄 → 거리·방향 계산
          └─▶ Pi  "jetson/aim"      발사관을 그쪽으로 돌림 (실장비면 0.3초 뒤 부표 발사)
          └─▶ Pi  "jetson/detection" 사고 생성 → 상태 DETECT → WAIT (30초 카운트다운)
          └─▶ Pi  사진 업로드 (HTTP)
        Pi ─▶ 키오스크  "pi/accident/state = WAIT"  화면에 경고 + 카운트다운
        Pi ─▶ Jetson   "사고 진행 중" → Jetson 은 새 탐지를 멈춤

[1초~]  부표: 물에 뜨면 1초마다 위치 전송 (LoRa)
        Pi ─▶ 키오스크  "pi/buoy/position"  지도에 부표 점
        (60초 동안 부표가 조용하면 → "통신 두절" 기록)

[30초]  키오스크에서 취소를 안 누르면 → 상태 REPORT → 조난 신고 발송
        (지금은 시뮬레이션: OpenCPN 프로그램으로만 보냄. 실제 무선 조난 채널은 쓰지 않는다)

[언제든] 인터넷이 되면 Pi ─▶ EC2  사고·부표·사진 기록을 차례로 올림
        육지 관제 웹이 5초마다 새로 받아 지도에 표시

[끝]    키오스크에서 구조/종료 → 상태 CLOSE → 고정 글 정리 → Jetson 은 다시 탐지 시작
```

## 6. 연결별 설명

### 6.1 Jetson ↔ Pi — "눈과 두뇌"

**한 줄 요약**: Jetson 은 본 것을 MQTT 게시판에 올리고, 사진처럼 큰 것은 HTTP 로 Pi 에 직접 올린다.

**왜 이렇게?** 탐지·조준은 짧고 빨라야 해서 MQTT, 사진은 크고 하나도 빠지면 안 돼서 HTTP 로 나눴다.

| 게시판 (토픽) | 방향 | 배달 | 내용 |
|---|---|---|---|
| `jetson/detection` | Jetson → Pi | 꼭 (QoS 1) | 사람 발견: 위치, 거리, 신뢰도, 카메라, 발사 방향 |
| `jetson/aim` | Jetson → Pi | 빨리 (QoS 0) | 조준 방향: 좌우각(yaw), 위아래각(pitch) |
| `jetson/status` | Jetson → Pi | 꼭 + 고정 | 모델 버전, 초당 처리 장수, 좌우 카메라 정상 여부 |
| `pi/accident/state` | Pi → Jetson | 꼭 + 고정 | 지금 사고 상태 (진행 중이면 새 탐지 멈춤) |
| `pi/sensor/gps` | Pi → Jetson | 빨리 + 고정 | 배의 GPS 위치 (Jetson 에는 GPS 가 없다) |

- 조준이 "빨리(QoS 0)"인 이유: 0.2초마다 새 값이 오므로 하나 잃어도 다음 것이 곧 온다. 늦게 도착한 옛 조준은 오히려 해롭다.
- Pi 는 **2초보다 오래된 조준은 버린다.** 그래서 Pi 와 Jetson 의 **시계가 맞아야** 한다(Jetson 은 켤 때 Pi 시계에 맞춘다).
- Jetson 은 **배 GPS 가 없으면 탐지를 올리지 않는다.** 좌표를 지어내면 구조대가 엉뚱한 곳으로 가기 때문이다.
- 카메라 영상은 Jetson 이 직접 띄우는 작은 웹 서버(포트 8080)에서 키오스크가 받아 본다.

### 6.2 부표 ↔ Pi — "바다에 뜬 발신기"

**한 줄 요약**: 부표가 1초마다 19바이트짜리 위치 쪽지를 LoRa 무선으로 보내고, Pi 가 받아 기록한다.

**왜 LoRa?** 부표는 작은 배터리로 오래 버텨야 하고, 배에서 떨어진 바다에서 보내야 한다. LoRa 는 전기를 적게
쓰고 멀리 가는 대신 한 번에 아주 조금만 보낸다. 그래서 쪽지를 **19바이트**로 줄였다.

**쪽지(프레임) 모양 — 19바이트**

| 순서 | 내용 | 크기 | 설명 |
|---|---|---|---|
| 1 | 버전 | 1 | 규격 버전 (`0x10`) |
| 2 | 배 표식 (ship_tag) | 1 | "우리 배 부표" 표시. 배 ID 로 계산한 1바이트 |
| 3 | 순번 (seq) | 2 | 1씩 늘어난다. 빠진 쪽지를 셀 수 있다 |
| 4 | 위도 | 4 | ×10,000,000 한 정수 |
| 5 | 경도 | 4 | ×10,000,000 한 정수 |
| 6 | 측정 시각 | 4 | 초 단위 |
| 7 | 상태 | 1 | 버튼 눌림(사람이 잡았나) · GPS 잡힘 · 배터리 |
| 8 | 검사값 (CRC) | 2 | 쪽지가 전파 중 깨졌는지 확인 |

**무선 설정 (양쪽이 같아야 대화가 된다)**

| 항목 | 값 |
|---|---|
| 주파수 | 922.125MHz (채널 72, 한국 920MHz 대역) |
| 무선 속도 | 2.4kbps |
| 보드 ↔ 모듈 | 9600bps 시리얼 |
| Pi 쪽 포트 | `/dev/ttyAMA0` |

**Pi 가 쪽지를 받으면**

1. 검사값(CRC)이 틀리면 버린다 (전파 중 깨짐)
2. **배 표식이 다르면 버린다** (옆 배 부표) — 그래서 배를 새로 등록하면 부표도 새 표식으로 다시 구워야 한다
3. 진행 중인 사고가 없으면 버린다 (지난 사고 부표가 아직 떠 있는 경우)
4. 통과하면 기록하고, 키오스크에 부표 위치를 띄우고, 나중에 서버로 올린다
5. 60초 동안 쪽지가 없으면 "통신 두절" 로 기록한다

### 6.3 키오스크 ↔ Pi — "조종석 계기판"

**한 줄 요약**: 키오스크는 Pi 의 게시판을 구독해 화면을 그리고, 버튼을 누르면 명령 게시판에 글을 올린다.

**왜 이렇게?** 브라우저는 일반 MQTT 를 못 써서 **웹소켓(포트 9001)** 으로 붙는다. 상태는 대부분 **고정 글** 이라
키오스크를 껐다 켜도 들어오자마자 현재 화면이 바로 찬다.

| 화면에 보이는 것 | Pi 가 올리는 게시판 |
|---|---|
| 사고 상태 · 카운트다운 | `pi/accident/state` (고정) |
| 부표 위치 | `pi/buoy/position` (1초) |
| 부표 표류 예상 범위 | `pi/buoy/drift` (고정) |
| 배 위치 | `pi/sensor/gps` (1초, 고정) |
| 배 기울기 | `pi/sensor/imu` |
| 카메라·AI·흔들림·부표 연결 상태 | `pi/device/status` (5초, 고정) |
| 신고 진행 상태 | `pi/report/status` (고정) |
| Pi 가 살아 있나 | `pi/online` (고정, Pi 가 죽으면 유언) |

**버튼 명령** — `kiosk/command/<명령>` 게시판

| 버튼 | 언제 누를 수 있나 |
|---|---|
| 취소 (`cancel`), 지금 신고 (`report_now`) | 카운트다운 중(WAIT) |
| 구조 (`rescue`), 종료 (`close`) | 신고 후(REPORT) |
| 수동 신고 (`report_manual`) | 사고가 없을 때 |

- 키오스크는 답이 올 때까지 **2초마다 다시 보내고, 5초가 지나면 "시간 초과"** 로 본다.
- Pi 는 같은 명령을 두 번 받아도 **한 번만 실행** 한다(요청 번호로 구분).
- 배 등록·지난 사고 기록·사진·해양 정보는 HTTP(포트 8000)로 Pi 에 묻는다.

### 6.4 Pi → EC2 서버 — "배에서 육지로"

**한 줄 요약**: Pi 는 모든 기록을 먼저 배 안의 DB 에 쌓고, 인터넷이 될 때 조금씩 서버로 올린다.

**왜 이렇게?** 바다에서는 인터넷이 자주 끊긴다. 그래서 **배 안에서는 인터넷 없이도 전부 돌아가고**, 서버
전송은 나중에 따라가는 구조다. 끊겨 있는 동안 쌓인 기록은 사라지지 않고 기다린다.

1. **배 등록**: 처음 한 번, 등록 키로 배를 등록하면 서버가 ship_key(배 비밀번호)를 **딱 한 번** 준다 → 관리자가 승인하면 전송 시작
2. **기록 동기화**: 아래 9종을 10초마다, 한 번에 200행씩 올린다 (밀려 있으면 0.5초 간격)

   | 순서 | 기록 |
   |---|---|
   | 1 | 배 위치 |
   | 2 | 사고 |
   | 3 | 사고 상태 변화 |
   | 4 | 발사 결과 |
   | 5 | 부표 위치 |
   | 6 | 배 기울기(IMU) |
   | 7 | 통신 두절 |
   | 8 | 부표 표류 예측 |
   | 9 | 신고 |

   사고가 먼저 올라가야 그 사고의 부표·사진이 올라간다.
3. **사진**: 사고 사진을 압축 묶음(tar.gz)으로 올린다
4. **해양 정보**: 조류·바람 같은 해양 데이터를 받아 부표 표류 예측에 쓴다

- **육지 → 배 방향 연결은 없다.** 서버가 배에 명령을 보내는 기능은 문서에만 있고 구현되지 않았다.
- 서버는 같은 기록이 두 번 와도 한 번만 저장한다(중복 방지).
- ship_key 는 로그·화면·다른 통신 어디에도 내보내지 않는다.

## 7. 믿을 수 있게 만든 장치들

| 걱정 | 대책 |
|---|---|
| 전파 중 쪽지가 깨지면? | CRC 검사값으로 확인하고 깨진 것은 버린다 |
| 옆 배 부표 신호가 섞이면? | 배 표식(ship_tag)으로 우리 부표만 받는다 |
| 인터넷이 끊기면? | 배 안에 먼저 저장하고 나중에 올린다. 배 안 기능은 인터넷 없이 전부 돈다 |
| 같은 메시지가 두 번 오면? | 요청 번호·시각으로 한 번만 처리한다 (Pi 와 서버 둘 다) |
| 늦게 도착한 옛 조준 명령은? | 2초보다 오래된 조준은 버린다 |
| 화면을 새로 켜면 빈 화면? | 상태는 고정 글이라 들어오자마자 현재 상태가 뜬다 |
| 장치가 갑자기 죽으면? | 유언(LWT)으로 "죽었음"이 뜬다. 카메라가 15초 조용하면 "고장"으로 표시한다 |
| "안 붙였음"과 "고장"이 헷갈리면? | 장치 상태를 모름 / 고장 / 정상 세 가지로 나눠 보낸다 |
| 가짜 좌표로 신고되면? | 배 GPS 가 없으면 탐지를 올리지 않는다 |
| 배 비밀번호가 새면? | ship_key 는 등록 때 한 번만 받고, 어디에도 찍지 않는다 |

## 9. 지금 상태와 남은 과제

### 잘 되는 것
- 부표 펌웨어와 Pi 의 쪽지 규격이 **바이트 단위까지 일치** 한다 (테스트로 같은 값 확인)
- Pi ↔ 서버의 필드 이름이 서로 맞는다
- 인터넷이 끊겨도 기록이 사라지지 않는다
- ship_key 가 새는 코드 경로가 없다

### 고친 것 (2026-09-23)

| 문제 | 무슨 일이 있었나 | 지금 |
|---|---|---|
| Pi 메인 반복문에 오류 처리가 없었다 | DB 오류 하나로 **Pi 프로그램 전체가 멈췄다** | 그 바퀴만 건너뛰고 계속 돈다. 부표 쪽지는 하나씩 따로 처리해 하나가 실패해도 나머지는 살린다 (`b4e2f75`) |
| 서버로 보낸 묶음에 나쁜 행이 하나라도 있으면 | **좋은 행까지 200개를 통째로 버렸다** | 서버가 알려준 나쁜 행만 버리고 나머지는 다시 보낸다. 안 알려주면 반씩 나눠 보내며 나쁜 행을 찾는다 (`1587fd7`) |
| 서버의 "버전 안 맞음" 답을 Pi 가 몰랐다 | 멈춰야 할 때 기록을 버렸다 | 전송을 멈추고 기록은 지킨다 (`2b947c9`) |

### 고쳐야 할 것 (중요한 순)

| 우선 | 문제 | 무슨 일이 생기나 |
|---|---|---|
| 🔴 | DB 연결 하나를 여러 작업이 순서 없이 같이 쓴다 | 가끔 DB 오류가 난다(보고된 `InterfaceError`). 이제 Pi 가 멈추지는 않지만 그 바퀴의 일은 건너뛴다 |
| 🟡 | 부표는 지금 **일부러 가짜 GPS** 로 쓴다 (시연용, `FAKE_GPS 1`) | 가짜 모드에서 부표가 재부팅되면 측정 시각이 같은 값에서 다시 시작해, 한동안 쪽지가 "중복"으로 조용히 버려지고 가짜 "두절" 이 뜰 수 있다. 시연 중 부표를 껐다 켰다면 Pi 로그를 확인한다 |
| 🟡 | "통신 두절" 을 Pi·키오스크·관제 웹이 **각자 다르게** 판단한다 (60초 / 30초 / 브라우저 시계) | 같은 상황이 화면마다 다르게 보인다. 관제 웹에는 두절 기록이 아예 안 뜬다 |
| 🟡 | 키오스크가 규격 파일을 안 읽고 손으로 옮겨 적었다 | 몇몇 필드가 어긋나 좌표·사고 종류가 틀리게 보일 수 있다 |
| 🟡 | Jetson 이 끊긴 사이 사고가 끝나면 | Jetson 이 사고가 계속 열려 있다고 믿고 재시작 전까지 탐지를 멈춘다 |
| 🟡 | 부표 쪽 무선 설정값을 확인한 기록이 없다 | 실물에서 설정을 한 번 읽어 확인해야 한다 |
| 🟢 | 기존 문서 여러 곳이 코드와 다르다 | 부록 B 참고 |
