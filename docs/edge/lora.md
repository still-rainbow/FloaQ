# LoRa 부표 통신

부표(익수자 위치 송신) ↔ Pi(수신) 구간의 무선 규격과 하드웨어 시험 절차를 정리한다.
MQTT 구간은 [mqtt.md](mqtt.md)가 따로 다룬다. 매체가 달라 규약도 다르다.

관련 티켓: floaq-95 (LoRa 패킷 포맷 정의)

---

## 1. 왜 MQTT 규약을 그대로 못 쓰는가

MQTT 구간은 JSON 봉투(`Envelope<T>`)를 쓴다. LoRa에는 그대로 못 쓴다.

`BuoyPosition`을 JSON으로 직렬화하면 200바이트가 넘는다. 부표는 1Hz로 송신한다(IOT-05,
`config.BUOY_TX_SEC = 1`). LoRa는 airtime이 곧 비용이라 이 크기로는 대역이 감당하지 못한다.

그래서 LoRa 구간만 **고정 19바이트 이진 프레임**을 쓴다.

정본은 `iot/pi/floaq/contracts/lora.py`다. 이 문서와 어긋나면 코드가 맞다.

---

## 2. 왜 TLV가 아닌가

TLV(Tag-Length-Value)의 값어치는 하나다 — 수신기가 모르는 필드를 건너뛸 수 있다.
그게 값어치 있으려면 송신기와 수신기가 **따로** 버전업되어야 한다.

이 프로젝트는 그렇지 않다. 부표 펌웨어와 `adapters/lora.py`가 같은 저장소, 같은 팀,
같은 배포다. 모르는 필드가 올 일이 없다. 없는 문제에 필드당 2바이트씩 내는 셈이다.

크기 비교: 같은 내용이 고정 구조체면 19바이트, TLV면 29바이트다.

파서의 실패 방식도 다르다. 고정 구조체는 길이 검사 한 번과 `struct.unpack` 한 줄이다.
틀리면 즉시 드러난다. TLV 파서는 루프 + 길이 경계 검사 + 모르는 tag 처리 + 중복 tag
처리가 필요하고, 버그가 특정 조합에서만 나타난다. 익수자 위치 수신 경로에 그런 코드를
두지 않는다.

**확장이 필요해지면** `ver_type`의 버전 필드를 올린다. 구파서를 남기면 된다.
필드마다 상시 비용을 내지 않아도 확장할 수 있다.

## 3. 프레임 규격

빅엔디안 19바이트.

| 오프셋 | 크기 | 필드 | 인코딩 |
|---|---|---|---|
| 0 | 1 | `ver_type` | 상위 4비트 버전, 하위 4비트 메시지 종류 |
| 1 | 1 | `ship_tag` | `sha256(ship_id)` 첫 바이트 |
| 2 | 2 | `seq` | uint16. 전원 인가 시 0, 18.2시간마다 순환 |
| 4 | 4 | `lat` | int32, 1e-7 deg |
| 8 | 4 | `lon` | int32, 1e-7 deg |
| 12 | 4 | `measured_at` | uint32, Unix 초 |
| 16 | 1 | `flags` | bit0 `is_pressed` / bit1 `gps_fix` / bit2-3 배터리 / bit4-7 예비 |
| 17 | 2 | `crc16` | CRC-16/CCITT-FALSE, 0~16바이트 대상 |

```python
struct.unpack(">BBHiiIBH", payload)   # 19 B
```

### 3.1 빅엔디안을 명시하는 이유

`>`를 반드시 적는다. 네이티브 `@`(파이썬 기본값)는 컴파일러 정렬을 따라가서 Pi와 부표
MCU가 서로 다른 레이아웃을 만들 수 있다. 그 실패는 **조용하다** — 에러 없이 좌표가
엉뚱한 값으로 나온다.

빅엔디안 자체가 리틀엔디안보다 낫지는 않다. "network byte order = 빅엔디안"은 IP/TCP/UDP
**헤더** 규격이고, 애플리케이션 페이로드에는 해당하지 않는다. LoRaWAN·BLE·USB는 오히려
리틀엔디안이다. 여기서 빅엔디안을 고른 이유는 헥스 덤프가 필드 순서대로 읽히기
때문이다. 현장에서 로그를 눈으로 볼 때만 이득이 있고, 그 외에는 동전 던지기다.

```
10 c9 0007 14ef69da 4d58a268 6aa8c1c2 0e 6ca5
ver tag seq  lat      lon      time    fl crc
```

중요한 것은 어느 쪽을 고르느냐가 아니라 **양쪽이 같고, 그것이 명시적**이라는 점이다.

### 3.2 좌표를 int32로 스케일하는 이유

float32도 4바이트다. 크기는 같다. 그런데 float32는 유효숫자가 7자리뿐이라 경도
129도대에서 약 1m 오차가 난다. int32 × 1e-7은 같은 4바이트로 1.1cm다.
익수자 위치에 1m 오차는 받아들일 수 없다.

범위도 들어간다. lat 90 → 900,000,000. lon 180 → 1,800,000,000. int32 상한
2,147,483,647 안이다.

### 3.3 `accident_id`를 싣지 않는 이유

`accident_id`는 탐지 시점에 Pi가 만든다. 그때 부표는 발사관 안에 있고 다운링크가 없다.
**전달 경로가 없다.**

장전 중 유선으로 써넣는 방법은 실패 방식이 더 나쁘다. 쓰기가 실패해서 부표가 옛 ID를
갖고 나가면 Pi가 패킷을 100% 거부한다. 익수자 위치가 아예 안 들어온다.
잘못 붙는 것보다 나쁘다.

Pi가 `repo.active()`로 붙인다. 동시 사고 1건(E1, `uq_pi_accident_active`)이라 모호하지
않다.

### 3.4 `ship_tag`가 필수인 이유

남의 배 부표 패킷은 **깨끗하게 수신되고 CRC도 통과한다.** 그쪽에서 제대로 만든
패킷이기 때문이다. 걸러낼 곳이 여기밖에 없다.

이걸 빠뜨리면 남의 익수자 위치가 우리 사고에 기록된다. 데이터가 없어지는 것보다
틀린 데이터가 들어오는 쪽이 훨씬 나쁘다 — 구조대가 엉뚱한 좌표로 간다.

`seq`로는 못 거른다. 남의 부표도 0부터 센다.

**`hash()`를 쓰지 않는다.** 파이썬 문자열 해시는 프로세스마다 난수화되어
(`PYTHONHASHSEED`) 재시작할 때마다 값이 바뀐다. 부표 펌웨어에 박아야 하는 값이므로
어느 언어에서든 같은 값이 나오는 sha256 첫 바이트를 쓴다.
`tests/test_lora_codec.py`가 서브프로세스를 세 번 띄워 이걸 검증한다.

### 3.5 `session` 필드를 두지 않은 이유

한때 "이전 사고 부표가 바다에 남아 계속 송신하는" 경우를 막으려고 사고마다 바뀌는
1바이트를 검토했다. 넣지 않기로 했다.

- 부표를 회수하면 그 상황이 생기지 않는다
- 막더라도 무선 필드가 필요 없다. 부표 `seq`는 전원 인가 시 0부터 시작하므로,
  Pi가 "사고 시작 후 `seq`가 작은 첫 스트림에 고정"하면 된다. `adapters/lora.py`
  안에서 끝나고 프로토콜은 그대로다

`seq`가 uint16이라 18.2시간 뒤 순환해 다시 작아지는 구멍이 있으나, 그때쯤이면 부표
배터리가 먼저 끝난다.

## 4. airtime과 크기

LoRa는 바이트가 아니라 **심볼 단위로 양자화**된다. SF7 / BW125 / CR4:5 / explicit header
/ CRC on 기준:

```
n_sym = 8 + ceil((8*PL + 16) / 28) * 5
```

| 페이로드 | 심볼 | airtime |
|---|---|---|
| 12~15 B | 33 | 46.3 ms |
| **16~19 B** | **38** | **51.4 ms** |
| 20~22 B | 43 | 56.6 ms |
| 23~26 B | 48 | 61.7 ms |

16바이트와 19바이트의 airtime이 **같다**. 그래서 `ship_tag`도 `crc16`도 실질 무료다.
비트 패킹으로 더 줄여도 절약이 0이다.

15바이트까지 내리면 33심볼(46.3ms)로 10% 줄지만, 그러려면 `seq`를 uint8로 낮춰야 하고
순환 주기가 18.2시간에서 4.3분으로 떨어져 유실 감지가 망가진다. 10%에 그 값을 바꾸지
않는다.

> ⚠ 위 경계는 SF7 전용이다. SF를 바꾸면 분모 `4*(SF-2*DE)`가 바뀌어 전부 이동한다.
> SF 확정 후 다시 계산해야 한다.
>
> 🔴 **지금 모듈은 SF7이 아니다.** E22에 써넣은 air rate가 2.4k라 19바이트 airtime이
> 51.4ms가 아니라 200ms대다(§9.1). 아래 §5의 점유율·충돌 표도 그만큼 나빠진다.
> 이 절의 숫자는 air rate를 올린 뒤에야 맞는다.

## 5. 충돌

### 자기 충돌
없다. 부표 1개다(E1 동시 사고 1건, E5 재투하 없음).

### 남의 배 부표
LoRa에는 CSMA가 없다. 같은 채널 + 같은 SF + 시간 겹침이면 충돌한다.

부표 하나가 51.4ms × 1Hz = 5.14%를 점유한다. 순수 ALOHA 모델 기준 수신 성공률:

| 근처 부표 수 | 성공률 |
|---|---|
| 2 | 81% |
| 3 | 74% |
| 5 | 60% |

**이건 이론 하한이다.** LoRa에는 capture effect가 있어 한쪽이 약 6dB 강하면 강한 쪽이
복조된다. 우리 부표는 배에서 수백 m, 남의 배 부표는 km 단위라 실제 성공률은 이보다
높다. 실측해야 아는 값이다.

손실은 설계에 이미 들어가 있다. `pi/buoy/position`은 QoS 0이고 "한 개 유실돼도 다음
게 온다". 전멸하면 `BUOY_TIMEOUT_SEC = 60`이 두절을 판정하고 표류 추정
(`pi/buoy/drift`)으로 넘어간다.

### 대책
1. **송신 지터 (1순위).** 정확히 1.000초 주기면 두 부표가 한 번 겹친 뒤 락스텝으로
   계속 겹친다. ±50ms 랜덤이면 연속 충돌이 풀린다. 부표 펌웨어 한 줄이고 비용이 0이다.
   위 표는 지터가 있다는 전제다.
2. **`seq` 유실률 관측.** Pi가 `seq` 구멍을 세면 실제 손실률이 숫자로 나온다.
   `pi_buoy.rssi`도 함께 기록하므로 RSSI가 정상인데 유실이면 충돌, RSSI가 낮으면
   거리로 구분된다.
3. **배마다 채널 분리.** 부표가 자기 배 채널을 알아야 하므로 배마다 따로 구워야 한다.
   시연 범위에서는 과하다.

### 하면 안 되는 것
CR을 4:5 → 4:8로 올리는 것. 오류 정정은 강해지지만 airtime이 늘어 **충돌 확률 자체가
올라간다.** 충돌은 비트 오류가 아니라 심볼이 통째로 뭉개지는 것이라 FEC로 못 살린다.

### 6.1 실행

```bash
# 실물 E22 (Pi 5)
uv run python main.py --lora serial --lora-port /dev/ttyAMA2

# RSSI 바이트를 켜둔 모듈이면 (REG3 bit7)
uv run python main.py --lora serial --lora-rssi

# 라디오 없이 상류만
uv run python main.py --lora fake
```

`--lora off`가 기본값이다. 부표가 없는 상태에서 두절 경고가 뜨지 않게 하려는 것이다.

### 6.2 어댑터가 하는 일과 안 하는 일

하는 일은 넷이다.

1. UART 바이트에서 **19바이트 경계 찾기** (CRC 재동기)
2. `ship_tag` 로 남의 배 부표 걸러내기
3. `seq` 구멍으로 유실률 집계 (`LinkStats`)
4. 큐에 쌓아 두기 — `drain()` 이 통째로 가져간다

SQLite 쓰기도 MQTT 발행도 **하지 않는다.** 그건 메인 루프가 `orch.on_buoy()` 로 한다.
수신 스레드에서 DB 와 브로커를 만지면 `adapters/mqtt.py` 가 이미 피하고 있는 함정을
다시 밟는다.

> 🔴 **`readline()` 을 쓰지 않는다.** 19바이트 이진 프레임은 개행(0x0A)을 값으로
> 포함한다. 줄 단위로 읽으면 프레임이 중간에서 잘린다. 시험용 `LoRa/lora_test.py`
> 가 줄 단위였던 건 그게 텍스트 PING/ACK 이라서다.

### 6.3 두절 판정

`BUOY_TIMEOUT_SEC = 60` 을 넘기면 `pi_comm_loss` 행을 연다. 다음 프레임이 오면 닫고
`pi/buoy/drift` retained 를 지운다.

- **한 번도 안 받았으면 판정하지 않는다.** 투하 전이다. 안 막으면 모든 사고가
  두절로 시작한다
- **시계를 못 믿으면 판정하지 않는다.** RTC 없는 Pi 는 부팅 직후 `now` 가 과거라
  전부 "1분 넘게 안 왔다"로 보인다
- `threshold_sec` 을 행에 박제한다. 나중에 값을 바꿔도 지난 구간이 스스로 설명돼야 한다

표류 추정(`pi_drift_estimate`, `pi/buoy/drift` 발행)은 **아직 없다.** 두절 구간을
기록만 하고, 해양 데이터 기반 추정은 다음 작업이다.

## 7. 하드웨어 (Ebyte E22-900T22D)

| 항목 | 값 |
|---|---|
| 무선칩 | SX1262 |
| 주파수 | 850.125 ~ 930.125 MHz (채널 0~80) |
| 출력 | 최대 22dBm |
| VCC | 2.3 ~ 5.5V |
| **UART 로직** | **3.3V** — VCC를 5V로 줘도 신호선은 3.3V |
| 설정 모드 UART | 항상 9600 8N1 (모듈 설정과 무관) |
| 송신 전류 | 약 110~130mA |

### 7.1 배선 — Pi 5 직결 (수신 노드, 운영 경로)

`확정` 2026-09-18. 배 쪽 E22는 아두이노를 거치지 않고 Pi UART에 바로 붙는다.

| E22 | Pi 5 | 비고 |
|---|---|---|
| VCC | 5V | |
| GND | GND | |
| TXD | GPIO15 (RXD, 10번핀) | 크로스 |
| RXD | GPIO14 (TXD, 8번핀) | **Pi는 3.3V 로직이라 레벨 변환이 필요 없다** |
| M0 | GPIO23 | 통신 모드 = LOW |
| M1 | GPIO24 | 통신 모드 = LOW |
| AUX | GPIO18 | 유휴 시 HIGH. 전부 LOW면 전원이나 AUX 배선 문제다 |

> 🔴 **포트 이름은 배선이 정한다. 외우지 말 것.**
>
> | 포트 | GPIO | 헤더 핀 | 필요한 설정 |
> |---|---|---|---|
> | `ttyAMA0` | 14 / 15 | **8 · 10** | `enable_uart=1` |
> | `ttyAMA2` | 4 / 5 | 7 · 29 | `dtoverlay=uart2` |
>
> 엉뚱한 포트를 열면 **영원히 0 바이트**다. 그런데 그 증상이 "전파가 안 온다"와
> **똑같이 생겨서** 배선·안테나·채널을 번갈아 의심하게 된다. 2026-09-22에 그렇게
> 몇 시간을 태웠다 — 부표는 `TX seq`를 올리는데 Pi는 조용했다.
>
> 확인은 외우지 말고 도구로 한다:
> ```bash
> uv run python tools/uart_scan.py              # 전 포트를 훑어 바이트가 오는 곳을 찍는다
> uv run python tools/uart_scan.py --loopback   # E22를 빼고 TXD-RXD를 점퍼로 이어 핀만 시험
> ```
>
> 지금 구성은 **헤더 8·10번 = `/dev/ttyAMA0`** 이다(`adapters/lora.LORA_PORT` 기본값).
> `/dev/serial0`은 아니다 — Pi 4까지의 글이 전부 serial0이라 그대로 따라 하면 못 연다.

> 🔴 **TX와 RX를 바꿔 꽂으면 조용하다.** 오류도 경고도 없다. 위 표의 "0 바이트"
> 원인 중 실제로 걸린 것이 이것이었다(2026-09-22).
> ```
> E22 TXD  ->  Pi RXD      E22가 말하고 Pi가 듣는다
> E22 RXD  <-  Pi TXD
> ```
> Pi는 3.3V라 분압이 필요 없고, 바꿔 꽂아도 안 망가진다 — 의심되면 한 번 바꿔 볼 것.

> ⚠ **M0/M1을 GND에 납땜했다면 GPIO로 건드리지 않는다.** HIGH를 주는 것이 곧 단락이다.
> `SerialLoRa`의 `m0_pin`/`m1_pin` 기본값이 `None`인 이유다 — 핀을 준 경우에만 잡는다.

아두이노 쪽(아래)은 **부표 역할과 벤치 A/B 시험용**으로 남는다.

### 7.2 배선 (Arduino Uno R3)

| E22 | Uno | 비고 |
|---|---|---|
| VCC | POWER 헤더 **5V** | 3.3V 핀은 50mA 상한이라 부족하다 |
| GND | POWER 헤더 GND | |
| TXD | **D10** | 직결 |
| RXD | **D11** | **저항 필요** (아래) |
| M0 | GND (통신) / 3.3V (설정) | |
| M1 | GND (통신) / 3.3V (설정) | |
| AUX | 연결 안 함 | |

TXD/RXD는 **크로스**다. 모듈 TXD가 아두이노 수신(D10)으로 들어온다.

> 🔴 **D0 / D1을 쓰지 않는다.**
> Uno의 D0/D1은 USB 시리얼 칩(ATmega16U2)과 물리적으로 공유된다. 여기에 모듈을 물리면
> 스케치 업로드가 `avrdude: not in sync: resp=0x00`으로 실패한다.
> 이 프로젝트에서 실제로 밟았고, 선을 빼자 바로 복구됐다.

### 7.3 레벨 변환이 필요한 이유

Uno 출력은 0V ↔ 5V, E22 입력은 0V ~ 3.3V다. 5V를 넣으면 칩 내부 보호 다이오드를 통해
전류가 모듈의 3.3V 전원선으로 역류한다. 그 다이오드는 정전기 수준의 전류를 흘리라고
있는 것이라 열을 받고 서서히 망가진다. Ebyte 문서도 "5V TX 신호가 모듈 RX 핀을
태울 수 있다"고 적고 있다.

증상이 고약하다 — **당장은 되다가 나중에 죽는다.** "직결해도 되더라"는 말이 도는 이유다.

두 가지 방법이 있다.

**① 분압 (저항 2개)**
```
D11 ──[R1]──┬── E22 RXD
            │
          [R2]
            │
           GND
```
`V_out = 5V × R2 / (R1 + R2)`

| R1 | R2 | 결과 |
|---|---|---|
| 1kΩ | 2kΩ | 3.33V (이상적) |
| 같은 값 2개 | | 2.5V (E22 HIGH 판정선 약 2.31V 위, 동작함) |

**② 직렬 저항 하나 (Ebyte 권장)**
```
D11 ──[2kΩ]── E22 RXD
```
내부 클램프 다이오드가 전압을 3.6V 근처로 잡고, 저항이 전류를 제한한다.
`(5V - 3.6V) / 2kΩ = 0.7mA`로 다이오드가 충분히 감당한다.

**수신 노드는 레벨 변환이 필요 없다.** E22 TXD(3.3V) → Uno D10 방향은 Uno가 3.3V를
HIGH로 읽으므로 그대로 연결한다. 그래서 `lora_ping.py` 단방향 시험에는 분압
**1세트면 충분하다.**

> 이 절 전체가 **Uno에만** 해당한다. Pi 5는 GPIO 자체가 3.3V라 양방향 모두 직결이다.
> Pi에 5V 분압을 넣으면 오히려 HIGH 판정선 아래로 떨어진다.

### 7.4 전원

| | 전류 |
|---|---|
| Uno 자체 | ~50mA |
| E22 송신 (22dBm) | ~110-130mA |
| 합계 | ~180mA |
| USB 2.0 한도 | 500mA |

USB 전원으로 충분하다. 별도 전원이나 커패시터는 필요 없다. 리셋이 실제로 반복되면
그때 VCC-GND에 100uF 이상을 단다.

> ⚠ **3.3V 핀에서 VCC를 따지 않는다.** 온보드 레귤레이터 상한이 50mA다.
> `3V3`과 `5V`가 바로 옆칸이라 한 칸 밀리기 쉽다.

> ⚠ 안테나 없이 송신하지 않는다. PA가 손상된다.

## 8. 시험 절차

### 8.1 부품 없이 도구만 확인
```powershell
cd IoT\PI
python tools\lora_ping.py rx --link udp
python tools\lora_ping.py tx --link udp      # 별도 창
```

### 8.2 E22 설정 읽기 (모듈 1개면 된다)

무선을 쓰지 않는다. UART로 모듈에게 직접 묻는 것이라 상대가 필요 없다.

1. M0, M1을 GND에서 떼어 **3.3V 핀**에 연결 (설정 모드)
2. `iot/buoy/lora_uart_bridge` 업로드
3. 실행
```powershell
python tools\e22_config.py --port COM9 --read
```

주소 / NETID / UART 속도 / 공기속도 / 송신출력 / 채널(실제 주파수) / 전송모드 / LBT가
나온다.

### 8.3 채널을 한국 920MHz 대역으로

공장 기본값은 대개 한국 대역 밖이다. `freq = 850.125 + 채널` 이므로 채널 71이면
921.125MHz다. **Pi 쪽 모듈에는 채널 72(922.125MHz)가 들어가 있다(§9.1).
부표 쪽도 같은 값이어야 한다** — 하나만 달라도 패킷이 0개고 고장으로 오해하기 쉽다.

```powershell
python tools\e22_config.py --port COM9 --channel 71
```

**두 모듈 모두에 적용한다.** 주소·채널·공기속도·UART 속도가 하나라도 다르면 패킷이
0개다. 고장으로 오해하기 쉽다.

끝나면 M0, M1을 GND로 되돌려야 통신 모드가 된다.

### 8.4 A/B 링크 시험

호스트 2개가 필요하다. 한쪽이 보내고 한쪽이 받아야 한다.

```
송신: [PC] ─USB─ [Uno A] ─D11→[저항]→ E22 RXD        (E22 TXD 미연결)
수신: [PC] ─USB─ [Uno B] ─D10←──────── E22 TXD        (E22 RXD 미연결)
```

양쪽에 `iot/buoy/lora_uart_bridge`를 올린 뒤:

```powershell
python tools\lora_ping.py rx --port COM9      # 먼저
python tools\lora_ping.py tx --port COM10     # 별도 창
```

재는 것은 **도달 여부 / 유실률 / 깨진 줄 수** 셋이다.

거리 시험은 수신 노드를 고정하고 송신 노드를 들고 멀어진다.

> ⚠ 부표는 물 위에 있다. 안테나가 수면에 가까우면 지상 시험보다 거리가 훨씬 짧게
> 나온다. 실제 조건으로 다시 재야 한다.

### 8.5 규격 프레임 시험

포맷이 확정되면 `lora_ab.py`로 19바이트 프레임 자체를 검증한다. `ship_tag` 필터,
CRC 거부, `seq` 유실 집계가 모두 들어 있다.

```powershell
python tools\lora_ab.py b --link serial --port COM9
python tools\lora_ab.py a --link serial --port COM10 --drop 0.2
```

## 9. 현재 설정값과 진행

### 9.1 Pi 쪽 E22에 써넣은 값 (2026-09-18)

```
C0 00 09 | 00 00 00 62 03 48 13 00 00
```

| 주소 | 값 | 뜻 |
|---|---|---|
| 00H ADDH | `00` | |
| 01H ADDL | `00` | |
| 02H NETID | `00` | |
| 03H REG0 | `62` | UART 9600 8N1 / **air rate 2.4k** |
| 04H REG1 | `03` | 서브패킷 240B / **TX 10dBm** |
| 05H REG2 | `48` | 채널 72 → **922.125 MHz** (한국 대역) |
| 06H REG3 | `13` | LBT on / 투명전송 / **RSSI 바이트 OFF** |
| 07-08H | `00 00` | 암호화 키 없음 |

응답이 `C1`로 시작하는 같은 바이트열이면 성공이다.

이 값에서 바로 걸리는 것 셋:

1. **RSSI 바이트가 꺼져 있다.** `pi_buoy.rssi`가 전부 NULL이 된다. §5 "대책 2"가
   RSSI로 충돌과 거리를 구분하자고 했는데 그 근거가 없어진다.
   켜려면 REG3을 `0x93`으로. 그러면 수신 단위가 19바이트가 아니라 **20바이트**가 되므로
   `--lora-rssi`를 같이 줘야 한다. 안 맞추면 매 프레임 1바이트씩 밀려 전부 버려진다.
   dBm 환산은 `rssi_byte - 256`이다.
2. **TX 10dBm.** 최저 출력이다(`11`). 거리 시험 전에 REG1을 `0x00`(22dBm)으로.
3. **air rate 2.4k.** §4의 airtime 표는 SF7(51.4ms) 가정인데 2.4k에서는 19바이트
   순수 데이터만 63ms고 프리앰블·헤더까지 200ms대다. 1Hz에 LBT까지 켜져 있어 여유가
   좁다. REG0 하위 3비트를 `3`(4.8k)이나 `4`(9.6k)로 올리면 절반 이하가 되고 거리와
   맞바꾼다. **실측 후 정한다.**

## 10. 미정

| 항목 | 내용 |
|---|---|
| 920MHz 대역 요건 | LBT 채널인지 duty cycle 채널인지. air rate 2.4k면 점유율이 20%대라 1% 제한이면 크게 위반이다. 1Hz는 `확정`(IOT-05)이므로 포맷으로 해결되지 않는다 |
| air rate | 지금 2.4k. §4 표(SF7 51.4ms)가 이 값에서는 안 맞는다. 4.8k/9.6k로 올릴지 실측 후 결정 |
| RSSI 바이트 | REG3 bit7. 켜면 `pi_buoy.rssi`가 채워지고 수신 단위가 20바이트가 된다 (§9.1) |
| TX 출력 | 지금 10dBm(최저). 거리 시험 전에 22dBm로 |
| SF / BW / CR | §4 심볼 경계가 전부 여기 걸린다 |
| HMAC 채택 | 배별 키 4바이트면 `ship_tag`와 CRC를 모두 대체하고 스푸핑도 막는다. 20바이트가 되어 airtime +10% |
| 부표 MCU | 확정 전. 프로비저닝 시 MCU 고유 ID를 읽어 (시리얼 → ship_id) 매핑을 남긴다 |
| 부표 펌웨어 담당 | 미정. 지터·`seq`·`ship_tag` 구현 주체 |
| 표류 추정 | 두절 구간은 기록되지만 `pi_drift_estimate` / `pi/buoy/drift` 발행이 아직 없다 |
